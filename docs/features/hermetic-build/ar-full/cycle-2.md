## 1. Округлить доработки Xake

Цель — понять (прежде всего владельцу), что у нас с ресурсами, и собрать **достаточный** для AR вариант
(строковые и бинарные resx, `ResXFileRef`, ресурсы из `.projitems`), а ночные доработки разделить на:

- **безусловные** — нужны, чтобы AR собирался и работал, или чинят реальный баг;
- **только-для-идентичности** — порядок исходников/атрибутов, ключи pathmap/SourceLink, переводы строк,
  порядок фасадов, `/highentropyva`, `/subsystemversion`, дефолт langversion, регистр в deps.json и т.п.;
  оставляем лишь дешёвые и детерминированные, остальное откатываем или паркуем;
- **WPF** и **сателлиты** — паркуются на отдельных ветках;
- **спорные** (критик): факты хоста/SDK в описаниях, apphost машины импорта (BN1), `deployWith` копирует
  всё из папки, разрешение ссылок цепочкой частных случаев — решение по каждому.

Выход: `night-changes-triage.md` (часть 1 — ресурсы для владельца, часть 2 — таблица изменений по
категориям, часть 4 — минимальная «достаточная для AR» ветка поверх `feature/hermetic-build`). Затем
владелец читает и решает, что сливать; агенты собирают минимальную ветку и паркуют остальное.

## 3. Структура выходных папок скрипта

Цели: плоская простая структура, минимум копирования, минимум места на диске. Факты цикла 1:
`xake-ar/deploy/` — 11 ГБ и 44 170 файлов (закрытие зависимостей скопировано для каждого приложения и
теста), `out/` — 2.1 ГБ, bin/obj msbuild в мете — 12.7 ГБ, эталонные копии в `logs/` — 46 ГБ.

Предлагаемая раскладка: `out/<бренд>/<cfg>/<tfm>/` — одна папка на ячейку и TFM, все сборки рядом
(имена брендированы, конфликтов нет), приложения и тесты запускаются из неё без copy-local; копируются
только пакетные рантайм-ассеты, test data и config/runtimeconfig/deps.json, и только один раз на папку.
`deploy/` исчезает; `Locks.deployWith` сводится к «дополнить общую папку тем, чего в ней нет».
Пакетная раскладка для nupkg — описанием (что из общей папки идёт в какой пакет), не копированием.

**Прототип 2026-10-14** (`xake-ar` ветка `layout-proto`, `tests/results/2026-10-14-layout-proto/results.md`):
компиляция в плоскую папку на ячейку+TFM работает с текущим API (имена сборок не конфликтуют),
файлов 46 848 → 7 048, `du` 13.4 → 3.4 ГиБ, время то же. Но **запускать тесты из общей папки нельзя**:
4 из 25 net8.0 тестовых сборок меняют результат (три собраны против NUnit 3.14, а в папке 4.4; Chart
получает dll 0.6.6 из ds.documents.excel вместо пакета 0.6.1); на ячейку 11–12 рискованных конфликтов
версий (NUnit, Castle.Core 4/5, TestPlatform 17/18, System.Drawing.Common 6/8, System.Text.Json 8/10, три
разных `ActiveReports.config`). Одна папка на ячейку без TFM невозможна (одинаковые имена файлов у net472
и net8.0). На APFS копии — клоны, реальных байт в 11 ГБ `deploy/` было ~40 МБ; цена была в числе файлов
(на NTFS/ext4 копии реальные). **Рекомендация**: плоская папка на ячейку+TFM для вывода компиляции;
приложения и тесты — в своей папке из hard-link/клонов нужных версий. Нужное изменение Xake: `deployWith`
(S60) — копировать по локу, не «всё из папки», в заданную папку, без перезаписи; правило конфликтов по
версии сборки, не пакета (S61).

## 4. Когнитивная сложность `build.fsx`

Один экран не самоцель, но цели по сто строк — это сложно. Направление: библиотечный модуль с готовыми
правилами и рецептами (`import::`, `lock::`, `check::`, `build::`, `pack::`, раскладка, бренды, extra
roots) в `Xake.Hermetic.Dotnet`; в скрипте остаётся объявление «какие проекты, бренды, конфигурации,
корень, раскладка» и редкие исключения. Pack — минимальный: nuspec как есть + токены из описания, без
`nugetManifest`/psmdcp/`pack-tokens` через msbuild.
