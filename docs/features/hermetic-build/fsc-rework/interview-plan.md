# build.fsc.fsx rework: interview plan

Eight questions for the user, ordered from the shape of the idea down to the script text. Each
one names the remark(s) it answers, the facts that narrow it (from digest.md, line numbers of
the PR's `build.fsc.fsx`), and the sub-questions that decide something. Fixed and not reopened:
`Csc` record, `resolve` op, no hooks, `CSC_SERVER`, `NUGET_FETCH`, package
`Xake.Hermetic.Dotnet`.

The user's remarks (verbatim):

1. Очень многословно, много бойлерплейта из коробки (например, основной таргет для бинарников).
2. Нетривиальные манипуляции с путями (`Path`), что должно понятно и просто выполняться средствами Xake.
3. Манипуляции с данными внутри кода таргетов (mapped, produced).
4. Общая идея не вполне уловлена. Интересен сценарий (не отрицая предложенного) для импорта проекта и генерации кода либо описания (зависимости, сорцы), которые далее коммитятся в репу.
5. Старые таргеты упаковки используют `dotnet pack`: выглядит так, будто сборка запускается заново мимо герметичных бинарников; возможно, сборка nuget тоже должна быть переведена на герметику.
6. Проверить на большом эксперименте, как будет выглядеть сборка ActiveReports для двух вендоров, насколько просты будут скрипты.
7. Идея описаний из п. 4 в папке проекта, для изоляции частностей проектов от рецептов сборки.
8. Сильное желание исключить nuget.org и публикацию, чтобы изолироваться от внешнего мира и не дёргать публичные пакеты.

## Q1. A per-project description in the project's folder (remarks 4, 7)

Facts: today the only description is `locks/xake.json`, ~240 lines per project, mostly
reference paths with SHA-256 (digest §3). Import already extracts everything a description
would hold: ordered sources, direct packages with versions, project refs, defines, TFM,
assembly name, version, variant properties (`Brand`). The PR deleted an earlier data form,
`projects/netstandard2.0/*.json` (read by the retired `Fsproj`). The composed `fsc { src; ref;
targetfwk; resolve }` is a third form where the script itself is the description.

Sub-questions:
- Content: sources (explicit list or glob + order), package refs with exact versions, project
  refs, defines, TFMs, variants (brand/vendor), assembly name/version, package metadata
  (license, icon, readme)? Anything msbuild-specific kept (generated AssemblyInfo, resources)?
- Form: F# (e.g. `src/core/project.fsx` loaded by the script, typed, an `fsc {}` value) or data
  (JSON/TOML) read by Xake? Is it meant to be edited by people or only read in review?
- Location: next to the fsproj (`src/core/...`) as remark 7 says; one file per project, or per
  project and variant?
- Does the build recipe then contain zero project specifics (no `libraries` list, 59-62)?

## Q2. Who runs import, who commits, what is primary (remark 4)

Facts: now fsproj is primary, `update-locks` (154) is a repeatable deliberate step after each
fsproj/props/package/global.json change, the diff is reviewed. Import needs msbuild, the SDK
and feeds (breaks offline, digest §8).

Sub-questions:
- One-off: import once, generate the description, then edit it by hand and drop fsproj/msbuild
  from the build (but IDEs and `dotnet test` still use fsproj)?
- Or repeatable: fsproj stays primary, the description is regenerated by `update-locks` and is
  a reviewable projection?
- If both stay, who wins on conflict, and is there a check (like `check-locks`) that they agree?
- For ActiveReports (Q5) the answer may differ: their teams edit csproj in IDEs daily.

## Q3. Lock vs description (remark 4)

Facts: the lock carries what review cannot check by eye (hashes, SDK-internal paths, msbuild
imports). The composed route already derives a lock from a description (`Lock.record`/
`Lock.build`/`Lock.verify`, workflows-ru §4).

Sub-questions:
- One layer (the lock only, perhaps made more readable) or two (description -> lock derived)?
- If two: is the lock still committed? Which file do PR reviewers read: the description diff,
  the lock diff, or both? Is the lock then generated without msbuild (from the description, as
  composed `fsc {}` does) or still by msbuild import?
- Does byte identity with `dotnet build` remain a goal (only the msbuild-import route gives it;
  fsc-design §6)?

## Q4. Hermetic packing (remark 5)

Facts: `pack` runs `dotnet pack` twice (236-265): full msbuild restore + build of net462 and
netstandard2.0, ignoring `out/` from `build`; the shipped nupkg and the tests use msbuild
binaries. `Pack.nupkg output nuspec files options` exists (byte-reproducible) but takes a
ready nuspec and an explicit file list; no nuspec generation, no `.snupkg`, signing is a
skeleton. `checkXakeDependency` (94-105) exists only because `dotnet pack` writes the nuspec.
net462: the lock imports netstandard2.0 only (56); dataengine already locks net472, so adding
net462 is an import option (references under `HERMETIC=on` unverified).

Sub-questions:
- Build nupkg from `build`'s outputs with `Pack.nupkg`: yes/no? Then net462 must be in the
  lock: acceptable?
- Nuspec: generated from fsproj metadata / the description (Q1), or a committed `.nuspec` per
  package? Dependencies (FSharp.Core, `Xake [3.6.0.24, 3.7)`) from the lock's direct packages?
- `Xake` nupkg carries two assemblies (core + Xake.Dotnet): stays one package?
- Tests: should `test` also run against hermetic binaries, or is `dotnet test` acceptable?
- Is a byte-identical nupkg across two clean builds the acceptance criterion?

## Q5. ActiveReports two-vendor experiment (remark 6)

Facts: existing scripts are proofs, not product builds: `verify-dataengine.fsx` 215 lines
(3 projects x 2 TFMs x 2 brands, 12 assemblies, SBOM), `import-page.fsx` 235 lines (page 12 +
dataengine 3 across sibling repos, `$(DataEngineRoot)`, `LocalBuild=true`). Same remap code as
`build.fsc.fsx` 198-213. Available locally under `~/Projects-work/ar/`: ar-net-core-dataengine,
-document, -page, ar-net-docs, -installer, -web-designer, -web-viewer, ar-net-win, -win-qa,
ar-web-designer(-qa-automation), arsamples, sample-ar-webapi. dataengine uses
`Directory.Packages.props`; page has `packages/`, `NuGet.Local.config`, `CycloneDX.targets`.

Sub-questions:
- Scope: dataengine + page (+ document?) only, or further (win, web)? Which branch (develop)?
- "Two vendors" = MESCIUS and GCCN brands, as in the existing scripts?
- Product scope: compile only, or pack + sign + SBOM per brand too? Tests?
- Cross-repo: project references (`LocalBuild`) or packages between repos?
- Success criteria: script size (lines, one screen?), byte identity with their msbuild build,
  time vs `dotnet build`, zero project specifics in the recipe (Q1)?
- Order: do the experiment before or after reshaping Xake's own script?

## Q6. Isolation from nuget.org (remark 8)

Facts: touch points: `#r "nuget:"` bootstrap (28-29), import restore (154), replay restore of
what `.packages` lacks, `dotnet test`/`dotnet pack` restores, push to nuget.org (274, 284,
publish.yml). Available: `NUGET_FETCH=off`, `Restore.into` + `Lock.restore` to fill a folder,
`nuget.config` for private feeds (restore goes through `dotnet restore`). Only compile-read
packages are restored, not the whole graph. Import and fsi bootstrap still need a feed or a
pre-filled folder.

Sub-questions:
- Source of packages: private feed (which?), a package folder committed in the repo, a sibling
  repo of packages, or a build-agent cache?
- How a new package version enters: a deliberate "fetch" step by a person with network, then
  committed/uploaded?
- Publishing target instead of nuget.org: private feed, folder, release artifacts? Does Xake
  itself stop publishing to nuget.org, or only ActiveReports?
- Bootstrap of Xake for `dotnet fsi`: from the same folder/feed, or from `out/` of a previous
  build (note 17-20: loading `out/` while overwriting it crashes fsi)?
- Should `HERMETIC=on` imply `NUGET_FETCH=off` on CI?

## Q7. Acceptable boilerplate (remarks 1-3)

Facts (digest §4-6): `build` target (140) + `binaries` (68-73); compile rule 180-220 with
`intermediate`/`unbuilt`/`produced`/`mapped` (198-211), package-root plumbing (189-190,
217-218), manual `HermeticMode.enforce` (214-216); `check-locks` 20 lines (157-176);
`Path.Combine` with `ProjectRoot` (87, 162, 184), `GetRelativePath` (213); `projectVersion`
regex (38-40); paired pack/push targets with hard-coded ids (225-287). Roadmap: "Rules with
arguments"; gap 6 "no one-call build of a whole imported lock", "no document-level Lock.diff".
The empty-hash test for project refs (199-202) is the one verify-dataengine rejected (decide by
name).

Sub-questions:
- Out of the box: "build everything in this lock" (with output layout as a parameter)?
  `check-locks`/`update-locks` as ready targets? HERMETIC gate inside `Lock.compile`?
- Paths: is `out/(fwk:*)/(lib:*).dll` as the only layout statement enough, with Xake mapping
  msbuild's `obj/` outputs and project refs itself?
- Rules with arguments: go ahead with the roadmap form, as part of this rework?
- What may stay in the script: version vars, package list, push target, test commands?
