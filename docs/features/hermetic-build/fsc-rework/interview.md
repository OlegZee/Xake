# build.fsc.fsx rework: interview log

Questions follow [interview-plan.md](interview-plan.md); facts in [digest.md](digest.md).
Each entry: question, the user's answer, decision (if one was taken). No design proposals until
the interview ends.

Started 2026-10-11.

## Q1. A per-project description in the project's folder (remarks 4, 7)

Asked: content, form (F# vs data), who reads it, location, whether the recipe then holds no
project specifics.

Answer (2026-10-11):

1. Content. The direct analogue is Bazel: the description holds what the project is and
   should change very rarely. Packages are pinned only when there is a need. Details can live
   in the build script; no need to invent optionality in the description. Ideal: one or two
   recipes serving a dozen projects.
2. Form. Data only, but preferably an ML-like format with typing. Wish: load descriptions
   dynamically, so the main script depends less on the projects (otherwise every project
   change edits the main script); to be thought over. Edited by a person or by a script
   (import from the project).
3. The recipe holds no list of libraries, sources or defines. But optionality of the same
   libraries may appear at some point (e.g. debug builds); how to handle that is open.

Open points: dynamic loading of descriptions; per-configuration optionality (debug).

## Q2. Who runs import, what is primary (remark 4); and what "ML-like data" means

Asked: one-off import then hand-edited description (fsproj no longer drives the build) vs.
repeatable import after each fsproj edit; who wins on conflict; check that they agree; same
answer for ActiveReports?  Clarifier on the format: F# record syntax as data, or another typed
config language.

Answer (2026-10-11):

- Format: ML-like with typing is the aim; JSON with a schema is fine to start with.
1. Repeatable: fsproj changes with every added module, so import is re-run; it can be a target
   in the build script itself.
2. That also settles consistency: if the description did not change in content, the file is
   not rewritten (no churn, nothing to review).
3. ActiveReports: daily csproj edits need investigating; likely for other reasons (e.g.
   debugging the SBOM build machinery), not the usual project change.

Decision: fsproj stays primary; the description is a projection regenerated by a target of the
script, written only when its content changes.

## Q3. Lock vs description (remark 4)

Asked: two layers (description from import, lock with hashes derived from it) or one; is the
lock still committed; which file is reviewed in PRs; is the lock derived without msbuild (from
the description, like composed `fsc {}`), giving up byte identity with `dotnet build`.

Answer (2026-10-11):

1. Two layers, of course: descriptive (human-readable) and executive (for the machine).
2. Yes, byte identity with `dotnet build` is given up. The hermetic mechanism arguably should
   have been built fully apart from the existing fsc/csc tasks; the intent, though, was
   integration: two sources of truth, fsproj and build.fsx. Hence a **fork**:
   - later, separately: a system for hermetic builds of existing csproj/msbuild projects,
     without pulling in csc/fsc (the msbuild-import route);
   - **now**: Xake's own system for a meaningful, declarative build description on the fsc/csc
     tasks. Layers: (a) script + descriptions, (b) generation of lock files, (c) build from
     locks. At (c) both forks meet: the lock format and the recipes are the same.
3. Reviewed through the git diff (both are committed).

Decisions:
- Focus of this rework: declarative build on fsc/csc; layers (a) script + descriptions,
  (b) lock generation, (c) build from locks.
- Lock format and lock-building recipes are shared with the future msbuild-import system.
- Byte identity with `dotnet build` is not a goal here.
- Descriptions and locks are committed; review is the git diff.

## Q4. Hermetic packing (remark 5)

Asked: nupkg from the binaries layer (c) produced, via `Pack.nupkg`, no second msbuild run;
where package metadata lives (description vs script); net462 as one more target of the same
description; nuspec dependencies from the description; tests against hermetic binaries or
`dotnet test`; byte-identical nupkg as the acceptance test.

Answer (2026-10-11):

1. Yes: nupkg from layer (c) binaries via `Pack.nupkg`, no second msbuild run.
2. Package metadata goes into the project description, overridable in the script (e.g. a
   common copyright or product name).
3. net462: just a second TFM, or a second scenario over the same project description.
4. `dotnet test` is acceptable for tests.
5. Yes, byte-identical nupkg across clean builds, but build time and build number must be
   ignored (Xake has to learn to tell those differences apart).

Decisions: hermetic pack from (c) binaries; metadata in the description with script overrides;
`dotnet test` stays; acceptance = nupkg identical modulo build time / build number.

Clarifier (answered with Q5): fsproj -> description: an SDK is acceptable and msbuild is
preferred for the import, but on CI these steps must be excluded (CI builds from committed
descriptions and locks only).

## Q6. Isolation from nuget.org (remark 8)

Asked: package source (private feed / folder in repo / sibling repo / agent cache); how a new
version enters (deliberate fetch step); publishing target instead of nuget.org, for Xake itself
too?; bootstrap of Xake for `dotnet fsi`; `HERMETIC=on` implying `NUGET_FETCH=off` on CI.

Answer (2026-10-11):

1. Isolation meant only *publishing* Xake. Package restore keeps using public nuget.org.
2. A deliberate fetch step sounds right, but it does not exclude going to the network for
   missing packages. Full hermeticity is the user's choice.
3. Applies to both Xake and ActiveReports: while the work is in progress nothing is published;
   instead a local shared folder, which also serves as the package source (local feed).
4. Bootstrap of Xake for `dotnet fsi`: no isolation needed.
5. `HERMETIC=on` does not imply `NUGET_FETCH=off`: separate axes.

Decisions: restore from nuget.org stays; no publishing during the work, a local shared folder
is both the publish target and a local feed; hermetic mode and fetching stay independent.

## Q7. Acceptable boilerplate (remarks 1-3)

   Xake. But the 40/20 lines of code are unwanted too. Targets should not contain data-processing

2. Rules with arguments: do it with what exists now; sugar later.
3. Debug/Release: part of the target mask.
4. The script keeps all of it: version, packed packages, metadata overrides, test commands,

Decisions: no data-processing code in targets; output layout chosen by the script, not
hard-wired; configuration lives in the target mask; no new rules-with-arguments sugar now.

## Review round 2: committed generated files (2026-10-11)

Critique given: (1) committed rule outputs vs the `.xake` database (fresh clone/CI = "Not built
yet" => import on CI); fixes: input fingerprints and/or a frozen mode; (2) floating package
versions make lock regeneration non-deterministic: "stale vs description" and "refresh
versions" are different acts; (3) the real import inputs are known only to msbuild; (4) should
a developer's `build` pull the import by itself. Variant A breaks when B lacks A's config, when
B targets another TFM (nearest match), across repos; fix: lock generation picks B's config/TFM
and records it in A's lock; the script maps (cfg, fwk, name) to a path only.

Answer:

1. Likes both mechanisms. Fingerprints (hashes) look easy in Xake's database, but `.xake` must
   not be committed, and storing the hash inside the file is too particular. So: a separate
   fingerprint file for artifacts that are kept in the repository; some declaration of what is
   stored in the repo turns on recording their hashes automatically, or optionally derived from
   `.gitignore`. Frozen mode is a reasonable direction, but a particular problem's solution
   should not go into Xake's core; only a general solution would: "rules over rules".
2. Agreed: both forced regeneration and disabling updates are needed. Pinning exact versions
   prevents involuntary regeneration, but explicit reference refresh matters (known from npm).
   Probably the case to do *without* a rule.
3. Accepted as another counterexample against generating through rules.
4. Not really wanted. A rule may *warn* that regeneration is needed, but not regenerate
   automatically. Scenario: a user may decide not to include a `xake.project.json` change in a
   commit, and still not want the local build to differ from what runs on CI.

Decisions:
- Descriptions and locks are produced by explicit commands (import, lock update), not by
  rules that fire on their own.
- Staleness of committed generated files is detected and reported as a warning; the build uses
  the committed files, the same as CI.
- Xake engine (general, not hermetic-specific): fingerprints for repository-kept artifacts in a
  separate committed file; which artifacts is declared, or optionally derived from `.gitignore`.
- Frozen mode stays out of the core unless a general mechanism ("rules over rules") is found;
  open design topic.
- Variant A fix: the lock of A records the chosen config/TFM of each referenced project.

## Fable review (review.md) and the user's answers (2026-10-11)

Review findings: (1) `kept` is frozen mode renamed, a particular mechanism in the core;
(2) brand-neutral descriptions + brand applied at lock generation by prefix rename was invented
and fragile; (3) package resolution is net new for composed fsc/csc; (4) staleness blind to C#
default globs, one repo-wide fingerprint file conflicts, CRLF; (5) nupkg equality across build
numbers impossible (version in dlls), no lock format bump/migration, `.xml` Debug bug.

Answers:

- Not `kept` but `cached`: "we cache the result in the repo". Do not index sources (fragile,
  huge file, many reads). A point solution is better: explicitly declare "this is expensive to
  compute, cache it keyed by its inputs".
- Caching as a **decorator on a rule**, attached with a pipe. The recipe checks that the file
  exists and (optionally) whether it needs updating, but the key point: when the file exists it
  does not trigger the target and hands back the file. Hopefully no engine change, only
  functions, maybe a cache in the internal context. This is variant (в), a rule combinator.
- Brands are a particular mechanism, expressed by **target prefixes**: different output paths
  and command prefixes like `clean::mescius`.
- Package resolution (finding 3): previously done by hand, inconvenient. Integrating it
  directly into fsc/csc makes no sense: it implies a multi-step build (a separate restore step +
  an implicit mechanism resolving paths before the build), which is better done with msbuild.
- Q1 of the review: decorator as above. "Agreed on (б) now and (в) later."

Decisions:
- Committed generated files: a `cached` rule decorator (pipe), keyed by declared inputs, no
  source indexing; when the file exists the target is not triggered; staleness check optional.
- Brands: target prefixes (paths + command prefixes), script knowledge.
- No package resolution inside fsc/csc; packages are resolved by msbuild (restore/import).

Clarified:
1. `cached` comes as the next step; first: explicit `import`/`locks` commands + a staleness
   warning.
2. Brands: import runs per brand (with that brand's props); descriptions and locks are stored
   separately per brand.

Remaining review questions:
3. C# sources: keep the glob in the description; it is expanded through a dependency on Xake's
   file search mask. The expansion (when it is an input) probably has to be materialised and
   hashed.
4. nupkg equality: compare by binary content only. CAS possibly later; assembly versioning in
   general is a topic still to be solved.
5. Fingerprints: the simplest option, one file, but one line per target (git-friendly).
   Lock format: the user sees no reason for a change; asked what changes.

## Implementation session 1 (2026-10-11): lock generation as a script rule

Context: PR #48 landed `Locks.generateAll` (library function: topological order over all
descriptions, loop over configurations and frameworks, one lock each). The user, after a
detailed walk-through of #48:

- Prefers to write the lock-generation rule by hand in the script and the sample projects
  ("it should be simple"), with the ordering between projects based on Xake targets, not on a
  sort inside the library. Reason: flexibility in defining the build target (adding settings)
  in scenarios and rules.
- The kept-versions / `LOCK_REFRESH` logic is liked and stays.
- `Locks.generate` (the one-lock primitive) could take the layout (`outOf`) and the lock's
  name/configuration from the recipe context instead of parameters.
- Asked to study: variant 1 (a file rule for the lock while `build` depends on the lock only as
  an input, never as a target) and phony rules (they do not run twice per build) as the
  carrier of lock generation.

Status: research delegated (`engine-locks-rule.md`); #48 not to be merged as is; decision on
the rule shape pending the research.

Decision (2026-10-11, after `engine-locks-rule.md`): **variant 2, phony rules**. Lock
generation is a parametrised phony rule in the script (`lock::(name:*)::(cfg:*)` or similar),
`alwaysRerun` allowed, ordering through `need` of the referenced projects' phony targets; it
runs only when the user explicitly invokes the `update-locks` target. `build` keeps reading
locks through `Lock.load` (`needFiles`): no file rule matches `locks/...`, so nothing is
generated on a fresh clone or CI. `Locks.generateAll` is removed; the library keeps the
one-lock primitive (`Locks.generate`) with kept versions and `LOCK_REFRESH`. #48 is reworked
in place. Why: flexibility to add settings per target in scenarios and rules; the library
must not own the loop or the ordering.
