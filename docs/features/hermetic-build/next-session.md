# Следующая сессия: переработка `build.fsc.fsx`

Стартовый документ для новой сессии Claude Code с чистым контекстом. Написан 2026-10-11 в
конце длинной сессии. Карта документации: [../../index.md](../../index.md), карта этой папки:
[index.md](index.md).

## Цель

Проанализировать и переработать идею `build.fsc.fsx`: герметичная самосборка Xake через lock.
Делается через интервью с пользователем.

- Сначала анализ и вопросы. Код, планы и PR только после явных решений пользователя.
- Вопрос или замечание пользователя это повод подумать и обсудить, а не команда менять код
  (память: `discuss-before-planning`).
- Решения по API, принятые 2026-09-29..10-07, не пересматривать (память:
  `hermetic-api-decisions`): запись `Csc`, операция `resolve`, без хуков, `CSC_SERVER`,
  `NUGET_FETCH`, пакет `Xake.Hermetic.Dotnet`.

## Замечания пользователя к скрипту (повестка)

Дословно, это и есть повестка интервью:

1. Очень многословно, много бойлерплейта из коробки (например, основной таргет для бинарников).
2. Нетривиальные манипуляции с путями (`Path`), что должно понятно и просто выполняться
   средствами Xake.
3. Манипуляции с данными внутри кода таргетов (mapped, produced).
4. Общая идея не вполне уловлена. Интересен сценарий (не отрицая предложенного) для импорта
   проекта и генерации кода либо описания (зависимости, сорцы), которые далее коммитятся в репу.
5. Старые таргеты упаковки используют `dotnet pack`: выглядит так, будто сборка запускается
   заново мимо герметичных бинарников; возможно, сборка nuget тоже должна быть переведена на
   герметику.
6. Проверить на большом эксперименте, как будет выглядеть сборка the trial product для двух
   вендоров, насколько просты будут скрипты.
7. Идея описаний из п. 4 в папке проекта, для изоляции частностей проектов от рецептов сборки.
8. Сильное желание исключить nuget.org и публикацию, чтобы изолироваться от внешнего мира и не
   дёргать публичные пакеты.

## План интервью

Задать до любых предложений, по одному-два вопроса за раз, ответы записывать в `session.md`.

1. **Описание проекта в его папке (пп. 4, 7).** Что в нём должно быть: исходники, ссылки на
   пакеты с версиями, ссылки на проекты, defines, варианты (бренды, TFM)? Это F#-код (модуль,
   который подключает скрипт) или данные (JSON/TOML), и кто его читает, Xake или человек?
2. **Кто запускает импорт и кто коммитит (п. 4).** Импорт это разовая генерация, после которой
   описание правится руками и msbuild больше не нужен, или повторяемый шаг (`update-locks`) после
   каждой правки fsproj? Что первично: fsproj или описание?
3. **Lock и описание (п. 4).** Lock остаётся единственным описанием (машинным, с хешами), или
   нужен второй, читаемый человеком слой, из которого lock выводится? Если два, что из них
   ревьюят в PR?
4. **Герметичная упаковка (п. 5).** Из чего собирать nupkg: из бинарников, которые уже собрал
   `build` (через `Pack.nupkg` и nuspec), без второго прогона msbuild? Что делать с net462-ассетом
   и с метаданными (лицензия, иконка, readme, зависимости), которые сейчас даёт `dotnet pack`?
5. **Эксперимент the trial product, два вендора (п. 6).** Какие репозитории (repo-a, page, ещё?),
   какие ветки, есть ли доступ из этой машины (`~/path/to/*`), какой масштаб (число
   проектов, TFM, брендов), и что считать успехом: размер скрипта, байтовая идентичность, время?
6. **Изоляция от nuget.org (п. 8).** Источник пакетов: приватный фид, папка пакетов в репозитории
   (или соседнем репо), кэш агента? Как появляются новые версии пакетов, кто их туда кладёт?
   Публикация: куда вместо nuget.org, и сам Xake для bootstrap скрипта тоже не с nuget.org?
7. **Допустимый бойлерплейт (пп. 1-3).** Что должно быть «из коробки» в Xake: таргет «собрать все
   бинарники из lock», маски путей вместо `Path.Combine`, правила с аргументами из roadmap? Что
   допустимо оставить в скрипте?
8. **Как скрипт читается новичком.** Каким должен быть идеальный `build.fsc.fsx` на одном экране:
   набросать вместе «желаемый» текст скрипта до реализации, и от него вывести недостающее в Xake.

## Организация сессии: оркестратор и субагенты

Контекст одной сессии ограничен, поэтому сессия работает как **оркестратор на Fable** и сама
читает только это: `docs/index.md`, индексы папок, этот файл, последние два раздела
`session.md`. Всё токеноёмкое делегируется субагентам (см. память `orchestrate-only`):

- **Чтение и выжимки.** Субагент читает скрипт из PR #42, `locks/xake.json`, `workflows.md` §B,
  `lock.md`, `fsc-design.md` §6 и возвращает выжимку в файл
  `docs/features/hermetic-build/fsc-rework/digest.md` (что делает скрипт, где бойлерплейт, какие
  манипуляции с путями и данными, что из этого должен уметь сам Xake). Оркестратор читает только
  выжимку.
- **Подготовка интервью.** Субагент уточняет восемь вопросов ниже по выжимке и добавляет
  конкретику (строки скрипта, примеры), результат в `fsc-rework/interview-plan.md`.
- **Интервью** ведёт оркестратор: только он может говорить с пользователем. По одному вопросу,
  ответы сразу записываются в `fsc-rework/interview.md` (вопрос, ответ, решение, если принято).
  Никаких предложений дизайна до конца интервью.
- **Эксперименты и черновики** (желаемый вид скрипта на один экран, пробный импорт, проба
  the trial product): субагенты, каждый со своим worktree, результат в файл; оркестратор получает
  отчёт, а не файлы.
- **Бриф.** После интервью субагент пишет `fsc-rework/brief.md`: решения, желаемый скрипт,
  чего не хватает Xake, план маленьких PR.

**Запланированный рестарт.** Когда бриф готов, оркестратор не начинает реализацию в этой же
сессии: он обновляет `session.md` (где мы и точный следующий шаг), пишет `next-session-2.md`
(цель: реализация по брифу; порядок чтения: индексы, бриф, interview.md; правила те же) и
заканчивает ответом с командой запуска новой сессии. Так интервью и реализация идут с чистым
контекстом каждая. Если контекст подходит к концу раньше, рестарт делается в ближайшей точке,
где всё собранное уже записано в файлы.

Правила для worktree и веток в этой сессии: один worktree на один PR, папка называется как
ветка; после мержа оркестратор даёт пользователю команду удаления; временных веток `work/*` и
`prep/*` не заводить; таблица «PR, ветка, worktree» живёт в `session.md`.

## Правила работы в сессии

- Сначала обсуждение; решает пользователь. Действовать только по явному решению.
- Небольшие PR в `dev` на OlegZee/Xake, squash. Не делать force-push и rebase.
- Конвенция папки фичи (память `feature-folder-convention`): перед концом сессии обновить
  `session.md` (где стоим, точный следующий шаг), `tracker.md` держать в актуальном виде.
- На длинных прогонах работу отдавать агентам, решения оставлять себе (память `orchestrate-only`).
- Решения по API не открывать заново (память `hermetic-api-decisions`).
- Отвечать по-русски. Документацию в `docs/` (кроме `-ru` файлов) писать по-английски.
