Анализ зависимостей и агент базы: как сейчас и как предлагается

Кто кого вызывает, какие сообщения пересекают границу агента базы, сколько их за запуск и кто делает файловый ввод-вывод. Ниже то же самое для предложенного разделения обязанностей. Числа сняты на бенчмарке bench/build.fsx: 1 188 файловых целей по 150 зависимостей, 6 групп, -t 16.

185 000 → ~8сообщений агенту за холостой запуск
189 000 → ~3 600сообщений агенту за полную сборку
181 764 → 0stat файлов внутри агента за холостой запуск
2.3 с / 0.6 схолостой запуск: 5.0 против 4.0 (полная сборка: 5.5–8 с против 0.4 с)

Значения «после» — расчёт по дизайну, их ещё нужно подтвердить прототипом. Значения «сейчас» измерены.

1. Как устроено сейчас

Есть четыре модуля движка и один агент. Агент базы (Storage, Database.fs) — это MailboxProcessor: он владеет таблицей результатов, таблицей файлов (FileRec), эпохой и файлом .xake. Сообщения ему посылают напрямую из трёх модулей, через ctx.Db; у базы нет своего API-слоя.

Собственная работа агента в полной сборке — 1.1–1.3 с. Ещё 4.1–4.7 с он готов работать, у него в очереди 100–140 сообщений, но поток пула ему не достаётся. В 4.0 этих сообщений не было: время файла читалось в вызывающем потоке.

Получается, что анализ зависимостей и ExecCore знают протокол агента (сообщения, каналы ответа, хэширование и Settle), а агент делает файловый ввод-вывод. Вердикт синхронный, а мемо держит один замок на весь обход.

2. Предлагаемые слои

Решение «изменился ли файл» становится чистым правилом и выполняется в вызывающем потоке, как в 4.0 сравнение по списку зависимостей. База ничего не решает: хранит записи, применяет изменения атомарно (compare-and-set) и пишет их в .xake. Читают её без сообщений, из опубликованного снимка. Хэши считаются за отдельным мейлбоксом. Состояние «что уже видели в этом запуске» принадлежит запуску. Каждый слой вызывает только слои ниже себя.

3. Интерфейсы по слоям

L0–L1: диск и правило

type FileStat =
  | Missing
  | Present of stamp * size
val FileStat.take : File -> FileStat
val Content.hash  : File -> HashResult

type Decision =
  | Keep of FileState option
  | Write of FileState
  | NeedHash
// чистые функции: сегодняшние правила
// observe и settle агента, без изменений
val decide : known -> FileStat
   -> ObserveMode -> RuleContext -> Decision
val decideHashed : known -> HashResult
   -> ObserveMode -> RuleContext -> Decision
val classify : since -> FileState option
   -> Observation

L2–L3: база и хэши

type Snapshot =
  { Status : Map<Target, BuildResult>
    Files  : Map<File, FileState>
    Epoch  : int }
// чтение без сообщений
val snapshot : Db -> Snapshot

// запись: CAS по каждому файлу,
// ответ — конфликты с текущей записью
Apply of (File * expected * new) list
Store of BuildResult   // с ответом
NewRun · InMemory · Close

// L3: один хэш на (файл, stat)
val Hasher.hash : File -> FileStat
   -> Async<HashResult>

L4–L6: запуск, фасад, вердикты

type RunFiles =
  member SeenByVerdict  : File -> bool
  member RecordedBefore : File -> bool

// L5: stat → правило → хэш → Apply
val observe : ctx -> ObserveMode
   -> since -> File list
   -> Async<Observation[]>
val getResult : Db -> Target
   -> BuildResult option
val store : Db -> BuildResult
   -> Async<unit>

// L6
type Verdicts =
  member Of : Target
     -> Async<ChangeReason list>
  member Warm : Target list -> Async<unit>
  member Estimate : Target
     -> int<ms> * Target list

Наблюдение группы файлов (L5)

sequenceDiagram
  participant C as Вызывающий (вердикт или need)
  participant S as Снимок базы

  participant A as Агент базы
  C->>C: stat каждого файла (L0)
  C->>S: записи файлов, эпоха (без сообщения)
  C->>C: decide для каждого файла (L1, RunFiles)
  opt есть NeedHash
    C->>H: hash(file, stat), параллельно
    H-->>C: HashResult (один расчёт на файл и stat)
    C->>C: decideHashed
  end
  opt есть Write
    C->>A: Apply [(file, ожидаемая запись, новая) × N]
    Note over A: CAS по каждому файлу, один Write в .xake
    A-->>C: конфликты
    C->>C: по конфликту: свежий stat, решить заново (до 3 раз)
  end
  C->>C: classify since → Observation[]

В холостом запуске все stat совпадают с записями: решения Keep, хэшей нет, Apply не отправляется. Агент не получает ни одного сообщения на файл.

Ожидаемое время

  • Холостой горячий: ~0.1–0.2 с (4.0: 0.56–0.64 с). На зависимость: stat 1.1–1.7 мкс, поиск в Map ~0.5 мкс и правило, на нескольких потоках.
  • Полная сборка: сообщений агенту в ~50 раз меньше. Нужно измерить, перестанет ли агент простаивать в очереди пула.

Что не меняется

  • Формат .xake и какие записи пишутся: правило L1 — сегодняшнее.
  • Эпохи, since, cut-off, один хэш на (файл, stat).
  • --dryrun, --dump, причины вердикта и их порядок.

Что меняется в поведении

  • У пересекающихся запусков движка свои RunFiles; сейчас NewRun второго очищает множества первого.
  • Задача ждёт ответа Store: иначе зависимая цель может прочитать старый снимок.
  • API: UpToDate async; у агента остаются Apply, Store, NewRun и служебные сообщения.

6. Порядок работы и открытые вопросы

  • Шаг 1, L0–L1. Чистое правило и табличные тесты, перенесённые из StorageTests. Агент пока вызывает правило сам, поведение не меняется.
  • Шаг 2, L2–L5. Снимок, Apply, Hasher, RunFiles, фасад. Затем замер холостого запуска и полной сборки.
  • Шаг 3, L6–L7. Асинхронный вердикт и мемо, прогрев, вызывающие.
  • Открыто: свой поток для агента (по замеру после шага 2); структура быстрее Map для таблицы файлов.

Объём: ~600 строк кода (агент теряет ~150) и ~400 строк тестов. Каждый шаг проверяется и ревьюится отдельно. Подробности по слоям — в docs/features/idle-perf/design.md.
