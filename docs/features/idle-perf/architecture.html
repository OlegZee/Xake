Анализ зависимостей и агент базы: как сейчас и как предлагается

Кто кого вызывает, какие сообщения пересекают границу агента базы, сколько их за запуск и кто делает файловый ввод-вывод. Ниже то же самое для предложенного разделения обязанностей. Числа сняты на бенчмарке bench/build.fsx: 1 188 файловых целей по 150 зависимостей, 6 групп, -t 16.

185 000 → ~3 700сообщений агенту за холостой запуск
189 000 → ~12 000сообщений агенту за полную сборку
181 764 → 0stat файлов внутри агента за холостой запуск
2.3 с / 0.6 схолостой запуск: 5.0 против 4.0 (полная сборка: 5.5–8 с против 0.4 с)

Значения «после» — расчёт по дизайну, их ещё нужно подтвердить прототипом. Значения «сейчас» измерены.

1. Как устроено сейчас

Есть четыре модуля движка и один агент. Агент базы (Storage, Database.fs) — это MailboxProcessor: он владеет таблицей результатов, таблицей файлов (FileRec), эпохой и файлом .xake. Сообщения ему посылают напрямую из трёх модулей, через ctx.Db; у базы нет своего API-слоя.

Собственная работа агента в полной сборке — 1.1–1.3 с. Ещё 4.1–4.7 с он готов работать, у него в очереди 100–140 сообщений, но поток пула ему не достаётся. В 4.0 этих сообщений не было: время файла читалось в вызывающем потоке.

Получается, что анализ зависимостей и ExecCore знают протокол агента (сообщения, каналы ответа, хэширование и Settle), а агент делает файловый ввод-вывод. Вердикт синхронный, а мемо держит один замок на весь обход.

2. Предлагаемое разделение обязанностей

Правило одно: каждый слой знает только слой под собой. Агент базы — хранилище с решениями в памяти, без чтения файлов. Модуль базы прячет агента за функциями и делает в вызывающем потоке всё, что связано с диском. Анализ зависимостей решает, что пересобирать, и работает только через функции модуля базы.

СлойОтвечает заНе делает
ExecCoreзадачи и их порядок, need, тела рецептов, выходы, сохранение результатане решает, актуальна ли цель; не посылает сообщения агенту
DependencyAnalysis (Verdicts)вердикт цели и его мемо на запуск, обход для оценки, критический путь, --dumpне делает stat и хэш; не знает сообщений агента
Модуль базы, фасад (Storage)stat и хэш в вызывающем потоке, батч-запрос агенту, батч-ответ, Settle, ожидание «занятого» файла, уборка при сбоене решает «изменился ли файл»: это решает агент
Агент базытаблицы результатов и файлов, эпоха, решение по stat (изменён / нет / нужен хэш), pending, запись в .xake одним Write на батчне читает файлы проекта; не ждёт никого

3. Интерфейсы

Модуль базы (фасад)

// Storage: публичный API для движка.
// Сообщения агента внутренние.
val newRun : Db -> hashing: bool
           -> Async<int>
val getResult : Db -> Target
           -> Async<BuildResult option>
// stat в вызывающем потоке, один батч,
// HashNeeded: хэш (параллельно) и Settle,
// Busy: повторно, с ожиданием в агенте
val observeMany :
    Db -> ObserveMode -> since: int
    -> File list -> Async<Observation[]>
val store : Db -> BuildResult -> unit
// делегированный: ответ — файлы без записи
val storeDelegated : Db -> BuildResult
           -> Async<unit>
val inMemory, closeWait : ...

Анализ зависимостей

// Вердикты одного запуска: каждая цель
// решается один раз, все ждут одну задачу.
type Verdicts =
  // NeedRebuild, UpToDate, зависимые
  member Of : Target
      -> Async<ChangeReason list>
  // начало группы: обход графа оценки
  member Warm : Target list -> Async<unit>
  // синхронно, после Warm: длительность
  // из уже загруженного результата
  member Estimate : Target
      -> int<ms> * Target list

val create : ExecContext -> current
      -> Verdicts
val criticalPath : ... // без изменений
val dumpDeps : ...      // --dump

Агент (внутренний протокол)

type FileStat =
  | Missing
  | Present of stamp * size

// ответ на каждый файл батча
type Reply =
  | Observed of Observation
  | Busy          // хэширует другой
  | Failed of string

Observe of (File * FileStat) list
        * ObserveMode * since
        * Reply<Reply list>
ObserveWait of File * FileStat * ...
Settle of HashRequest * HashResult * ...
GetResult · Store · StoreDelegated
NewRun · InMemory · Close

ExecCore получает Verdicts из beginRun и вызывает Of для вердикта задачи и быстрого пути. UpToDate становится Target -> Async<bool>. Для файлов без правила в need вызывается один observeMany Recording на весь список, для выходов — один на задачу. getDepState остаётся чистой функцией над уже собранными данными.

«~2 400» в холостом запуске: 1 188 батчей вердикта + 12 батчей групп + 1 188 одиночных наблюдений файла зависимой цели (по одному на ребро, их можно объединить позже). Сохраняется stat на каждую зависимость (ваше решение), поэтому stat переходят в вызывающие потоки, а не исчезают.

Ожидаемое время

  • Холостой горячий: ~0.3–0.4 с (4.0: 0.56–0.64 с). Stat распределены по потокам, агенту остаётся ~1 мкс на файл в памяти.
  • Полная сборка: ~1 с, если агент перестанет простаивать в очереди пула. Это не измерено; если простой останется, агент получает свой поток в этом же изменении.

Что не меняется

  • Формат .xake и записи FileRec.
  • Эпохи, cut-off, хэш один раз на файл.
  • Решения вердикта и порядок причин.
  • --dryrun, --dump, пересекающиеся запуски движка.

6. Открытые вопросы

  • Async или синхронный обход. Async убирает все блокирующие ожидания, но требует асинхронного мемо с защитой от циклов (блокер 2 критика). Синхронный обход с батчем на цель проще, но оставляет ~1 200 блокирующих ожиданий на запуск. Рекомендация: async.
  • Свой поток для агента. Решать по замеру прототипа батча (замечание M5).
  • Порядок stat. Stat снят раньше решения агента; устаревший stat не должен перезаписывать запись, обновлённую в этом запуске (M3).
  • Остальные замечания критика и предложения — в docs/features/idle-perf/design.md, §10.

Оценка объёма: ~400 строк кода и ~350 строк тестов. Порядок работы: сначала фасад с батчем и stat в вызывающем потоке и замер, потом асинхронный вердикт и мемо.
