# Sketch: hermetic path functions fed from typed patterns

Status: sketch only (brief decision 9: "not now, but show what it would look like"). No code
changed. Syntax is the prototype's (`experiments/03-type-provider/consumer/use.fsx`: `Path`,
`Make`, `All`, `Glob`, `Rule`, `Get`, `Text`); anything beyond it is marked **(new)**.

## 1. The functions today

The hermetic API takes the layout as curried functions, threaded through every entry point
(`generate`, `restoreAll`, `needAll`, `runFolder`, `runFolders`, and their `With` variants):

| function | defined | signature |
|---|---|---|
| `lockOf` | `build.fsc.fsx:25` `let lockOf name cfg = $"locks/{name}/{cfg}.json"` | `string -> string -> string` |
| `outOf` | `build.fsc.fsx:26` `let outOf cfg fwk (_: string) = $"out/{cfg}/{fwk}"` | `string -> string -> string -> string` |
| `flatOutOf` | `src/hermetic/Locks.fs:788` `sprintf "out/%s/%s" cfg fwk` | same shape, library default |
| `runOf` | `src/hermetic/Locks.fs:791` `sprintf "run/%s/%s/%s" cfg fwk name` | same shape |
| `OutOf` | `src/hermetic/Import.fs:755,761,961`: `sprintf "out/%s/%s/%s" cfg fwk name`, a field of `RecordOptions` | same shape |

Consumers append a file name to the returned folder: `Locks.fs:207`
`Path.Combine (outOf cfg refFwk name, e.Name + ".dll")`, `:230` (same with `assemblyName`),
`:763` (`needAll`), `:937,965` (run folder), `:1043-1053`
(`Path.Combine (runOf cfg e.Framework d.Name, RunFolder.Manifest)`; `RunFolder.fs:27`,
`let Manifest = ".xake-run.txt"`, not a `[<Literal>]`).

## 2. The rules they mirror, and the drift

| function | mirrored by | where the two meet |
|---|---|---|
| `outOf` | `target "out/(cfg:*)/(fwk:*)/(name:*).dll"` (`build.fsc.fsx:64`) | `Locks.fs` builds `outOf ... + <assembly>.dll` and `need`s it; the rule must match that string |
| `lockOf` | the phony `"lock::(name:*)::(cfg:*)"` (`:47`) writes `lockOf name cfg` via `Locks.generate` (`Locks.fs:181`); `Locks.compileAs (lockOf name cfg)` (`:68`) reads it | the lock file is no rule's target, only a side effect of the phony |
| `runOf` | a script's deploy rule (none in `build.fsc.fsx`; doc comment `Locks.fs:1043`) | the folder is only ever a `need`ed manifest path |
| `OutOf` (import) | the same layout, again | two library defaults (`Import.fs:761` three segments, `Locks.fs:788` two) plus the script's |

Drift the current code allows (each stays silent until a build asks for a target nobody makes):

1. `outOf` changed to `bin/{cfg}/{fwk}` while the rule stays `out/...`: `Locks.needAll` needs
   `bin/Release/net8.0/X.dll`, no rule matches; the failure is far from the edit.
2. `outOf` and `Import.RecordOptions.OutOf` disagree (the library already ships both shapes).
3. Argument order: all arguments are `string`, so `outOf fwk cfg` compiles. `lockOf` is
   name-first, `outOf`/`runOf` are cfg-first.
4. The rule's group `name` is passed to `lockOf name cfg` as the *project* name (`:68`), but
   `needAll` fills the path with the *assembly* name (`outputName e`, `Locks.fs:760-763`). They
   coincide here; with an `<AssemblyName>` different from the project name the rule would look
   for `locks/<assembly>/Release.json`. The string-function layout cannot show the difference.

## 3. Proposed: patterns as the source of truth

```fsharp
type Lock = Pattern<"locks/(name:*)/(cfg:*).json">
type Dll  = Pattern<"out/(cfg:*)/(fwk:*)/(name:*).dll">
type Run  = Pattern<"run/(cfg:*)/(fwk:*)/(name:*)/.xake-run.txt">      // see runOf
```

A pattern is a path to a file, so the three are *file* patterns; folders are derived (section 4).
Patterns must be `[<Literal>]` (decision 10); inline above for brevity.

### lockOf

Before: `let lockOf name cfg = $"locks/{name}/{cfg}.json"` (`build.fsc.fsx:25`), used at `:54,68`
and passed into `Locks.*`. After:
```fsharp
let lockOf name cfg = Lock.Path(name = name, cfg = cfg)      // by label: order cannot be swapped
do! Locks.compileAs (lockOf m.name m.cfg) m.fwk versions
```
Removed: swapped arguments at the call, a typo'd or forgotten group (FS0039 / FS0496). Not
removed: nothing ties `Lock` to the phony rule that writes the file (section 4).

### outOf

Before (`build.fsc.fsx:26,64-68`, `Locks.fs:207`):
```fsharp
let outOf cfg fwk (_: string) = $"out/{cfg}/{fwk}"
target "out/(cfg:*)/(fwk:*)/(name:*).dll" {
    let! cfg = getRuleMatch "cfg" ... do! Locks.compileAs (lockOf name cfg) fwk versions }
let output = full (Path.Combine (outOf cfg refFwk name, e.Name + ".dll"))
```
After, the *file* is generated by the pattern; the folder function and the `+ ".dll"` suffix
disappear from the library:
```fsharp
Dll.Rule(fun m -> recipe { do! Locks.compileAs (lockOf m.name m.cfg) m.fwk versions })
let output = full (Dll.Path(cfg = cfg, fwk = refFwk, name = e.Name))        // Locks.fs:207,230,763
```
Rule and `need` share one literal, so drift 1 cannot happen (change the literal, both move).
Drift 4 is exposed rather than fixed: rename the group `asm` in the literal and every
`lockOf m.asm` stops compiling, forcing the author to say which name the group holds.

### runOf

Before (`Locks.fs:791`, consumed `:1043-1053`):
```fsharp
let runOf cfg fwk name = sprintf "run/%s/%s/%s" cfg fwk name
normal (Path.Combine (runOf cfg e.Framework d.Name, RunFolder.Manifest))
```
After:
```fsharp
normal (Run.Path(cfg = cfg, fwk = e.Framework, name = d.Name))
// a script's deploy:  do! need (Run.All(cfg = ["Release"], fwk = frameworks, name = appNames))
```
The `.xake-run.txt` suffix moves into the literal, creating a pair with `RunFolder.Manifest`
that can drift. Either `Manifest` becomes a `[<Literal>]` and the pattern is concatenated from
it, or the pattern stays at folder level, with the manifest appended in code as today.

### Lists for `need`

| today | typed |
|---|---|
| `needAll` builds one path per project/framework by comprehension (`Locks.fs:757-763`) | `Dll.Path` inside the same comprehension. `All` is a cross product; the framework set comes from each lock, so it is not one and `All` does not apply |
| `update-locks`: `for name, _ in projects do do! need [ $"lock::{name}::Release" ]` (`:56`) | phony, section 4 |
| `restoreAll` / `runFolders` take a `Fileset` of descriptions | `Glob` returns a `Fileset` (decision 8); no current hermetic call site needs `Dll.Glob`, e.g. `Dll.Glob(cfg = "Release")` for a cleanup |

## 4. What does not fit

- **Phony names**: `"lock::(name:*)::(cfg:*)"` (`build.fsc.fsx:47`), `need [ $"lock::{r}::{cfg}" ]`
  (`:51`), `$"lock::{name}::Release"` (`:56`), doc comments `Locks.fs:160-167`,
  `docs/hermetic/lock.md:1638,1644`. The prototype yields file paths; a phony needs
  `Command<>`-style members (decision 5, **cost still open**), roughly `Lock.Need(name = r, cfg = cfg)`
  and `Lock.Rule(...)`. **Depends on the separate phony-type question**; only the `lock::`
  lines of this sketch wait on it.
- **The lock file** `locks/(name)/(cfg).json` is no rule's target (the `lock::` phony writes
  it), so `Lock.Rule` cannot register it; the pattern serves generation only. Making it a
  `FileRule` would change semantics (engine-tracked output, `alwaysRerun`, `Fingerprints.record`):
  out of scope.
- **Run-time-built patterns**: `RecordOptions.OutOf` is filled by the caller at run time; a
  layout read from configuration cannot be a literal. These keep the function form, and the
  pattern supplies a default function (`Dll.Path` as a first-class function works in the
  prototype, taking a tuple; a curried wrapper is needed for the current API).
- **Values with constraints**: `Make`/`Path` validate by matching the produced path back, at run
  time (research section 5): a `name` containing `/` fails there, not at compile time. These
  three patterns use only `*` groups, so no constraints or nesting are involved. Names such as
  `Xake.Hermetic.Dotnet` and `net8.0` are fine for `*`.
- **Roots and normalization**: the hermetic code mixes relative paths (`outOf`) with rooted ones
  (`full ...`, `Locks.fs:207,230`). `Dll.Path` returns the pattern-relative string with `/`
  (what `need` takes today); callers wanting a rooted path keep the `full` wrapper. On Windows
  `Path.Combine` yields `\`; matching normalizes, a string comparison would not (none exists now).
- **Folder vs file**: today's `outOf` returns a folder and ignores the project name (flat
  `out/{cfg}/{fwk}`, shared by all projects). A file pattern needs the `name` group. Folder-level
  uses (clean, `--output` to msbuild) would want **(new)** a derived folder view, or a second
  unrelated pattern `out/(cfg:*)/(fwk:*)`, which the type system will not tie to `Dll`.

## 5. Passing patterns into the library

`src/hermetic` cannot name script-defined provided types. Three ways, cheapest first:

1. **Keep the function API, supply it from the pattern.** `let outOf cfg fwk _ = Dll.Path(cfg = cfg, fwk = fwk, ...)`
   (a curried wrapper, as in the prototype's `outOf fwk lib`). No hermetic change; scripts get
   labelled generation and one literal, but the library still takes
   `string -> string -> string -> string`, so swaps inside the library and drift 2 remain.
2. **A small runtime record in `Xake.dll`** (the runtime half of the provider) **(new)**, e.g.
   `Layout = { Dll: ...; Lock: ...; Run: ... }`, built from the provided types. The library
   takes `Layout`; argument order is fixed by the record. Costs a new public type.
3. **The library takes pattern text and works by group name**: scripts pass `Dll.Text`; the
   library generates through the string API with reserved group names (`cfg`, `fwk`, `name`).
   The typed layer lives on the script side only; the library cannot drift but needs a
   documented set of reserved names, and a missing group is a run-time error again.

Recommendation: start with option 1 to prove the call sites, decide 2 vs 3 once the provider
exists.

## 6. What it would take

| file | option 1 | option 2/3 |
|---|---|---|
| `build.fsc.fsx` | literals/types; `lockOf`/`outOf` become one-liners; `Dll.Rule` replaces the `getRuleMatch` block (`:64-68`) | same, passing `Layout` / `.Text` |
| `docs/hermetic/*.md`, `docs/hermetic-guide.md`, `samples/hermetic/*`, doc comments `Locks.fs:160-167,300,736` | optional | rewritten to the new call |
| `src/hermetic/Locks.fs` | none | `generate*`, `restoreAll*`, `needAll*`, `runFolder*`, `runFolders*`: `lockOf`/`outOf`/`runOf` parameters replaced; `flatOutOf`, `runOf` (`:788,791`) become default patterns |
| `src/hermetic/Import.fs` | none | `RecordOptions.OutOf` (`:755,761,961,1007,1871`) replaced; one copy of the layout removed |
| `src/hermetic/RunFolder.fs` | none | `Manifest` promoted to a literal if the run pattern is file-level |
| `BuildFromLockTests.fs:21-23,351-352`, `RecordTests.fs` | none | local `lockOf`/`outOf`/`dll` helpers use the same literals |

Public API impact (`Xake.Hermetic.Dotnet`, 0.x preview):
- option 1: none, additive.
- option 2/3: breaking for every caller of the entry points that take path functions (about a
  dozen, plus `RecordOptions.OutOf`). Fine as a 0.x bump with a migration note; keep the old
  overloads for one release if external consumers exist.
- the package would need a minimum `Xake` version that ships the provider (check how the nuspec
  references Xake; not verified here).

Ordering against the core provider work:
1. Core provider first (`Pattern<>`, `Path`/`Make`/`All`/`Rule`/`Get`, labels, positional
   wildcards), in the `Xake` nupkg (decision 1).
2. Phony-type decision (decision 5, cost estimate); only the `lock::` lines wait on it.
3. Dogfood in `build.fsc.fsx` with option 1: no library change; shows whether drift 1 and 3
   really disappear (4 is exposed, 2 needs option 2/3).
4. Then `src/hermetic` (option 2 or 3) as its own PR with the migration note.

Open for the user: option 2 vs 3 at the library boundary; whether `Manifest` and the lock file
name become literals shared with the library; whether the flat `outOf` (unused project name) is
kept as a layout or replaced by the `name`-carrying `Dll`.
