Comparison: hermetic build output vs `dotnet build` baseline (split lock, 2026-09-23)
======================================================================================

The lock format changed with Stage B (docs/features/hermetic-build/csc-syntax.md, "Where a
Lock.Entry comes from"): one entry is Evaluation / Compilation / Dependencies, the command
line is structured (Options with section markers, Defines, Sources, References, Analyzers)
and rebuilt by `Entry.Args`, verified at import against msbuild's list; the package graph
is in the lock. This comparison re-proves the byte-identity of the outputs on that format.

Fixture:      `git archive origin/develop` copy of ar-net-core-dataengine, cleaned
              (`rm -rf locks src/*/obj .xake`) before the import.
Produced by:  dotnet fsi import.fsx -- -- build   (cwd = the copy; locks, then compile)
              Both locks + 6 dlls: 9.5 s from clean. Round-trip check passed for all
              6 entries (the rebuilt command line equals msbuild's).
Baseline:     dotnet build src/DataEngine/DataEngine.csproj -c Release -t:Rebuild
              -p:TargetFramework=netstandard2.0 -p:Brand=<B> -p:NuGetAudit=false
              -p:IntermediateOutputPath=obj/xake/netstandard2.0/<B>/
              run in the SAME checkout, same IntermediateOutputPath, per brand, with
              -t:Rebuild (see session.md: the page near-miss was msbuild's incremental
              cache reusing stale outputs), overwriting Xake's obj/xake outputs in place.
              Xake's outputs were copied to /tmp/xake-out/<B>/ beforehand and compared
              against what msbuild wrote.
