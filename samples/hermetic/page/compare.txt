Byte comparison: Xake's `import-page.fsx build` output vs a clean `dotnet build -t:Rebuild`
reference, both brands, page's 12 shipped projects + dataengine's 3 (netstandard2.0), 90 files
(dll/pdb/xml) total.

Re-run 2026-09-24 after the lock split (stage B)
--------------------------------------------------
The lock format was split into `Evaluation` / `Compilation` / `Dependencies` with the package
graph folded into `Dependencies.Packages`, and a bug was fixed in `Nuget.readAssets`
(single-`TargetFramework` projects key `project.assets.json`'s `targets` by the full framework
name `.NETStandard,Version=v2.0`, not the alias). The page fixture -- multi-target projects,
reference aliases, two repositories, two brands -- had not been re-run since. This file is that
re-proof. Method and result are unchanged from the previous run: **90/90 byte-identical**.

Preamble -- why this replaces the pre-`-t:Rebuild` table
---------------------------------------------------------
An earlier comparison here reported page's dlls differing from `dotnet build` in the
deterministic-hash fields. Root cause: that comparison ran `dotnet build` (not `-t:Rebuild`)
sharing Xake's own `obj/xake/...` intermediate folder, so `dotnet build`'s incremental caches
(`*.Up2Date`, `CoreCompileInputs.cache`) reused stale project-reference outputs left over from
a previous Xake run instead of rebuilding from the sources Xake actually compiled. The fix for
*this* comparison: `dotnet build -t:Rebuild`, run in place at the exact same
`-p:IntermediateOutputPath=obj/xake/netstandard2.0/<Brand>/` Xake itself used, so both builds
consume the identical restore/design-time-build inputs and there is nothing left over to hide
a real difference or manufacture a fake one.

Method
------
1. Clean the fixture: `rm -rf locks out .xake import.log src/**/obj/xake
   ../ar-net-core-dataengine/src/*/obj/xake` (dataengine's `bin/Release` outputs from earlier
   sessions were left in place -- see the note under "Locks" below).
2. `dotnet fsi import-page.fsx -- -- build` -- one command; the `build` phony needs both locks,
   which are imported concurrently, then compiles all 30 outputs.
3. Saved every dll/pdb/xml from `obj/xake/netstandard2.0/<Brand>/` (page's and dataengine's) to
   a side directory.
4. For each of the 12 page csproj + 3 dataengine csproj, both brands (30 builds, sequential):
   `dotnet build <csproj> -c Release -t:Rebuild -p:TargetFramework=netstandard2.0 -p:Brand=<B>
    -p:LocalBuild=true -p:NuGetAudit=false "-p:IntermediateOutputPath=obj/xake/netstandard2.0/<B>/"
    -nologo -v:m` -- in place, same intermediate path Xake used, so `-t:Rebuild` cleans and
   rebuilds from the identical inputs.
5. `cmp` every one of the 90 saved files against what step 4 produced in the same location.

Result: 90/90 files byte-identical (dll, pdb, xml; 12 page + 3 dataengine projects x 2 brands).

`0 unhashed` in this run because dataengine's `bin/Release/netstandard2.0/*.dll` were still on

state at import time, not of the lock format; it also means this run's SBOMs carry SHA-256 on
the project-reference file components where the previous run's had none.

Pre-existing lock defect, unchanged by the split (not a regression): `Evaluation.ProjectRefs`
holds 52 raw absolute paths per lock that do not exist on disk -- msbuild resolves a
`<ProjectReference Include="..\..\X\X.csproj">` against the *process* cwd (the page copy)
instead of the referencing project's directory, so page's own `src/Rendering/Rendering.csproj`
is recorded as `<page>/../Rendering/Rendering.csproj` and dataengine's as
`<page>/../../ar-net-core-dataengine/...`. Being wrong they are also un-tokenized (no root
matches). Same 52 in the pre-split lock, byte-for-byte the same spellings. Nothing reads
`ProjectRefs` -- the compile replays `Dependencies.References` -- so builds and SBOMs are
unaffected. It is the same class as the `<EmbeddedResource Update=...>` cwd bug already fixed
in `parseImport`; the fix was never applied to `ProjectRefs`.

Brand-dependent package ids (the concurrent-import race check): MESCIUS lock has 35 `ds.documents`
matches and 0 `gcdocs`; GCCN lock the exact reverse. No race in this run.

Earlier findings carried over (unchanged by the lock split)
==========================================================

MSBuildProjectExtensionsPath experiment (tracker: concurrent-import race)
--------------------------------------------------------------------------
Candidate fix for the known race (two brands importing the same project concurrently share
one `obj/project.assets.json`, and with brand-dependent package ids the wrong reference can get
recorded): add `"MSBuildProjectExtensionsPath", $"obj/xake/{framework}/{brand}/ext/"` to the
import's `Properties`.

Tried, and REVERTED -- it does not work. It does separate `project.assets.json` and
`<Project>.csproj.nuget.g.props/targets` per brand (confirmed: they land under
`obj/xake/netstandard2.0/<Brand>/ext/`), and it did stop the specific race the grep test
targets (ran `locks` from clean 3x with both brands concurrent: GCCN always recorded `gcdocs.*`
and 0 `ds.documents.*`; MESCIUS always the reverse -- see grep results below). But it broke
reference resolution for every project in the design-time build: with it in place, captured
`/reference` counts dropped from 113-134 per project (the implicit NETStandard.Library facade
set) down to 0-21 (only direct PackageReferences/ProjectReferences); the smallest project
(VBFunctionLib, which has no direct references of its own) then got a lock entry with *zero*
references and failed to compile with "Predefined type 'System.String' is not defined or
imported" for every file. Confirmed by A/B against the same clean tree with only that one
property differing. `nuget.g.props`/`nuget.g.targets` did NOT show up in any lock's `Imports`
either with or without the property (checked while it was in place). Left for the library
owner; not shipped in `import-page.fsx`.

Race-test grep results (all three from-clean concurrent `locks` runs, WITH the property in
place):
  Run 1: GCCN ds.documents=0, GCCN gcdocs=20, MESCIUS ds.documents=20, MESCIUS gcdocs=0
  Run 2: GCCN ds.documents=0, GCCN gcdocs=20, MESCIUS ds.documents=20, MESCIUS gcdocs=0
  Run 3: GCCN ds.documents=0, GCCN gcdocs=20, MESCIUS ds.documents=20, MESCIUS gcdocs=0
A fourth run, from clean, WITHOUT the property (the shipped state) also came back clean:
  GCCN ds.documents=0, GCCN gcdocs=20, MESCIUS ds.documents=20, MESCIUS gcdocs=0
(the race did not reproduce in this environment even unfixed -- it is timing-dependent; the
grep check is still worth keeping in the script's test loop for whoever chases it further.)

`..`-rule
---------
The former workaround -- a second, absolute-path file rule for dataengine's own compile
outputs, needed because a `..`-prefixed `target` pattern did not match -- is gone. With the
engine fix now in `.bootstrap/Xake.dll`, one relative rule handles both repositories' outputs:

    target "../ar-net-core-dataengine/src/(proj:*)/obj/xake/(fwk:*)/(brand:*)/(name:*).dll" { ... }

alongside the existing in-repo rule `target "src/(proj:**)/obj/xake/(fwk:*)/(brand:*)/(name:*).dll"`.
The two could not be folded into one pattern (different literal prefixes), but the absolute-path
workaround rule is removed. Verified: `build` produces all 30 outputs (12 page + 3 dataengine x
2 brands), zero errors.
