SBOM comparison: Xake's `sbom` rule vs page's own CycloneDX.MSBuild pipeline
=============================================================================
Fixture: ar-net-core-page + ar-net-core-dataengine siblings, netstandard2.0,
brands MESCIUS / GCCN. Xake script: docs/features/hermetic-build/import-page.fsx.

Re-run 2026-09-24, after the lock split (stage B)
--------------------------------------------------
The package graph now lives in the lock itself (`Dependencies.Packages`, folded
in at import); `Sbom.forAssembly cacheRoot entry assemblyPath` reads the lock
only and no longer opens `obj/project.assets.json` at sbom time (the assets copy
and the `ProjectAssetsFile` property hack are gone). Two visible consequences
for this comparison, both improvements:

  * **Package ids keep their original NuGet casing** (`System.Text.Json`, not
    `system.text.json`). The old wording below -- "ours all lowercase, because
    `Nuget.packageOf` reads them off the cache's lowercase directory names" --
    no longer applies: the ids come from the restore graph recorded in the lock.
    The casing difference against CycloneDX.MSBuild is gone.
  * **More packages, because the lock records the restore graph, not only what
    the compile linked.** Rdl/MESCIUS went from 9 purls to 12.

Part 2 (CycloneDX.MSBuild) was NOT re-run; `Rdl-MESCIUS-theirs.cdx.json` in this
folder is the same file from the 2026-09-23 run and is what the purl comparison
below uses. Everything else on this page is from the 2026-09-24 re-run.

Part 1 numbers
---------------
`dotnet fsi import-page.fsx -- -- sbom` (assemblies already built): 0.9 s,
30 `*.cdx.json` (15 lock projects x 2 brands), sizes 52.9 KB - 77.2 KB.
Every one has a non-empty `components[]` with purls -- the check the stage-B
`packages 0` bug would have failed. Purl count / top-level component count,
per project (identical for both brands except where brand-variant package ids
differ, see "Brand" below):

(The purl count of every project equals its lock entry's `packages N` -- the

Determinism: deleted the whole `out/` tree, re-ran the same `sbom` command,
`cmp` all 30 files against the first run -- **30/30 byte-identical**. Expected:
`Sbom.cycloneDx` never writes `metadata.timestamp` and derives `serialNumber`
from the document's own content.

Rdl/MESCIUS sample (Rdl-MESCIUS-ours.cdx.json)
------------------------------------------------
Root (`metadata.component`): `asm:MESCIUS.ActiveReports.Core.Rdl`, version
4.6.0, one SHA-256 of the built dll, no purl (it is the assembly Xake compiled,
not a NuGet package).

14 top-level `components[]`: 2 `file` (the two dataengine project-reference
outputs) + 12 `library` (the purls above). Both project-reference files carry a
SHA-256 in this run -- last time they had none. Nothing changed in the rule:
the lock records whatever evidence existed at import time, and dataengine's
`bin/Release/netstandard2.0/*.dll` happened to be on disk from an earlier
session, so the import hashed them. Build the fixture truly from scratch and
they go back to unhashed.

Root's `dependencies[]`: depends on `pkg:nuget/System.Memory@4.6.0` and
`pkg:nuget/System.Text.Json@8.0.5` (direct, required packages only).

`formulation`: one formula, `formula:compile:MESCIUS.ActiveReports.Core.Rdl`,
holding 5 components, all scope `excluded` -- 3 analyzer files (System.Text.Json's
Roslyn source generator, the two SDK NetAnalyzers) plus `tool:csc`
(4.11.0-3.25569.22) and the `.NET SDK` entry (8.0.425).

  Reading. `Microsoft.NETCore.Platforms` moved from "only theirs" into the
  common set: with the graph in the lock we now see restore-graph entries the
  compile never linked, which is what theirs reports too. `NETStandard.Library`
  is still ours-only -- a compile-time facade package (all referenced files under
  `ref/`); we list it scope `excluded`, theirs does not surface facade-only
  packages. The two build-time-only packages `CycloneDX.MSBuild` and
  `SauceControl.InheritDoc` are ours-only and scope `excluded`: they are in
  page's restore graph (they are the very tooling theirs is produced by) and we
  report them because the lock records the graph; theirs filters
  developmentDependency packages out. `Microsoft.NETFramework.ReferenceAssemblies.net472`
  and `System.ValueTuple` remain theirs-only: page's `TargetFrameworks` is
  `netstandard2.0;net472` and these two are in the *net472* leg of the restore
  graph, which the `NetCoreOnly=true` import never evaluates.

  Hashes: every package in ours has a SHA-512 (now read from the lock's
  `Package.Sha512`, not re-read from the cache); theirs has SHA-512 on all 11.
  Uppercase vs lowercase hex, cosmetic.

  Per-file evidence: theirs has none. Ours nests one `file` component per
  referenced dll under its owning package, SHA-256 each.

  Formulation: theirs has none. Ours always has one (5 entries here).

  Determinism: ours 30/30 identical across two runs (above). Theirs is not --
  fresh random `serialNumber` and wall-clock `metadata.timestamp` per run
  (measured 2026-09-23; not re-measured).

  Brand: brand never leaks into third-party package identity, and the two brands'
  purl sets are identical for 10 of the 15 projects. The other 5 differ by exactly
  the brand-variant package ids page itself declares (`DS.Documents.*` for MESCIUS,
  `GcDocs.*` for GCCN), which is the expected behaviour, not the concurrent-import
  race -- no cross-contamination in either lock:
    Drawing.Gc         DS.Documents.Imaging@9.2.1              <-> GcDocs.Imaging@9.2.1
    Drawing.Gdi        DS.Documents.{Imaging,Imaging.Windows,  <-> GcDocs.{Imaging,Imaging.Windows,
                       DX.Windows}@9.2.1                            DX.Windows}@9.2.1
    Export.Image.Page  same three as Drawing.Gdi               <-> same three
    Export.Pdf.Page    DS.Documents.{Imaging,Pdf}@9.2.1        <-> GcDocs.{Imaging,Pdf}@9.2.1
    Export.Svg.Page    DS.Documents.Imaging@9.2.1              <-> GcDocs.Imaging@9.2.1
  Root components stay brand-qualified (`asm:MESCIUS.…` / `asm:GCCN.…`).
